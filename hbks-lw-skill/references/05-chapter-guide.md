# 逐章写作手册（六章式系统类论文）

> 本手册解决“每一节到底写什么、写多长、拿什么证据写、写完怎么自检”。
> 规范条款以 `02-writing-standards.md` 为准；本手册是它的章节级施工图。

## 0. 总原则与篇幅

| 项 | 要求 |
|---|---|
| 写作顺序 | 先第 3 章（需求）→ 第 4 章（设计）→ 第 5 章（实现）→ 第 6 章（测试）→ 第 1 章（绪论）→ 第 2 章（技术）→ 结论 |
| 证据来源 | 源码、SQL、接口、运行截图、测试记录；每个事实能指回文件/路径/表名/接口 |
| 正文总字数 | **硬性红线：12000–16000 字**（第1章–结论，不含摘要/参考文献/致谢/附录）；多一个字少一个字都不行 |
| 各章预算 | 第1章 1200–1800；第2章 1000–1500；第3章 2000–2500；第4章 2800–3500；第5章 3000–3900；第6章 1400–1900；结论 600–900（下限合计 12000，上限合计 16000） |
| 段落 | 每段 3–6 句，一段只讲一个判断；不要一段到底，也不要一句一段 |
| 图表 | 第 3–4 章 ≥10 图（本模板固定 9 张标准图 + 每个实体一张属性图）；第 5 章每节 ≥1 张截图；第 6 章用表不用图 |

> 下面各节的“约 X–Y 字”是**相对权重参考**，不是逐节必须凑满的配额；每章以本章预算为准，写超时压缩重复内容，写少时补有证据的细节，最终以正文 12000–16000 为准。

**写作前先做三件事**：读 `paper-context/project-evidence.md`、确认技术栈清单、确认角色与核心业务闭环。没有证据的段落不写，先登记缺口。

**字数校准（12k–16k 红线）**：

- 字数口径：`check_manuscript.py` 按“中文字符 + 西文单词 + 数字串”估算正文（第1章–结论），包含正文段落、表格文字和图题注，不含摘要/参考文献/致谢/附录；最终以 Word 字数统计复核。
- Word 的“全文统计”包含封面、声明、摘要、目录、参考文献、致谢、附录，通常比正文多 1500–3000 字；**默认红线指正文**。如果学校明确按全文统计卡字数，先问清口径，再按该口径调整，不要直接拿全文统计去套 12000–16000。
- 字数不足：优先补“有证据的细节”——业务规则、异常/回退路径、数据流转、设计取舍、测试用例与断言、真实运行约束；**不要**靠重复背景、空泛意义、同义反复凑字。
- 字数超出：先删重复的文献综述与背景铺垫，合并同类模块小节，把大段代码/字段明细移到附录；不要删掉第4章设计论证和第6章测试证据。
- 每写完一章看 `check_manuscript.py --json` 里的 `stats.chapters`，对照本章预算；最后整体落回 12000–16000。

## 1. 第1章　绪论

### 1.1　研究背景（约 400–500 字，3–4 段）

1. 行业/场景背景：这个业务在现实中如何发生、参与者是谁、规模或痛点是什么。用具体场景，不要“随着信息技术飞速发展”。
2. 现有做法的问题：人工/表格/通用平台分别卡在哪（信息不透明、流程割裂、对账困难、管理端缺失等）。
3. 技术条件：为什么现在适合做（移动端普及、框架成熟、部署成本下降），但只写与本项目相关的。
4. 本课题的必要性：一句话收束到“因此有必要设计并实现……”。

**禁止**：从盘古开天写起；把第 2 章的技术介绍提前；空喊“具有重要意义”。

### 1.2　国内外研究现状（约 500–700 字）

按**主题/维度**组织，不按时间流水账。建议两个三级标题：

- 1.2.1 国外研究与发展现状：平台模式、关键技术、用户体验/治理经验；每个观点带具名文献 [n]。
- 1.2.2 国内研究与应用发展现状：同类系统/小程序/管理平台的做法与不足；同样带文献。

最后一段必须给出**差距**，例如：

> 现有研究多聚焦平台运营模式，对“设备库存—订单状态—支付回滚”这一业务闭环的系统实现讨论不足；部分系统重后台管理、轻用户端流程。本文据此把……作为重点。

**禁止**：只罗列“某某设计了某某系统”而不给结论；匿名引用“有研究指出”；编造文献。

### 1.3　本文研究内容与技术路线（约 350–500 字）

- 研究内容：功能范围（角色+模块）、技术范围（栈）、验证范围（测试）。
- 技术路线：需求分析→总体设计→数据库设计→编码实现→系统测试，每一步产出什么。
- 与章节对应：用一段话说明第 2–6 章各自解决什么问题，但**不要写成目录复述**。

**自检**：读完 1.3 能否说出“这篇论文做了什么、怎么做、怎么验证”。

## 2. 第2章　相关技术介绍

### 结构

按项目真实技术栈设 4–7 节（如 Spring Boot、Vue/Element UI、微信小程序、MyBatis-Plus、MySQL、JWT、文件上传、AI 接口）。**项目没用到的技术不要写**。

### 每节统一三段式（约 220–280 字，4–6 节合计约 1000–1500 字）

1. **是什么**：一句话定位 + 2–3 个关键机制（不是 API 手册）。
2. **为什么选它**：与替代方案比，结合本项目规模/团队/部署条件说明理由。
3. **本项目落点**：具体用在哪一层/哪个模块，解决什么问题；点出关键配置或设计取舍。

### 禁止

- 写成官方文档目录（“Spring Boot 有 starter、有自动配置……”）却不落到项目。
- 同一技术写两节；技术名拼写不统一（Spring Boot / SpringBoot）。
- 把“相关技术”写成“技术栈清单”，没有任何选型判断。

**自检**：每节最后一段必须能回答“所以本项目为什么用它、用在哪”。

## 3. 第3章　系统需求分析

### 3.1　系统总体需求分析

#### 3.1.1　用户角色分析（约 300–400 字 + 可选角色表）

- 列出角色（普通用户、管理员；若有商家/审核员也列出）。
- 每个角色：目标、能做什么、不能做什么、进入哪个端。
- 角色与权限的边界要能对应第 4 章鉴权设计和第 6 章权限测试。

#### 3.1.2　功能需求分析（约 700–900 字 + 图3.1、图3.2）

- 按业务阶段/模块写，不按代码目录写。每段：谁→在什么场景→完成什么→系统给出什么结果。
- 先写普通用户主线（浏览→下单→支付→订单→归还/评价），再写管理员主线（登录→用户/设备/订单/内容/配置）。
- 图3.1、图3.2 前必须有引导句，图后要有 1–2 句解释“图里为什么是这些用例”。
- 用例粒度：动词+对象；不要把“查看列表”和“查看详情”拆成两个用例，除非业务上确实不同。

#### 3.1.3　非功能需求分析（约 350–450 字）

按维度写，并给可验证的约束：

- 性能：常用列表/详情响应时间目标、并发量假设（合理即可，不编造实测）。
- 安全：登录鉴权、密码存储、越权控制、上传校验、敏感信息脱敏。
- 易用性：关键操作步数、错误提示、移动端适配。
- 可维护性：分层、统一返回、日志、配置外置。
- 兼容性：浏览器/微信版本/分辨率。

**禁止**：只写“系统要安全、要稳定、要易用”而没有可验证标准。

### 3.2　可行性分析

- 3.2.1 技术可行性：栈是否成熟、团队是否掌握、关键难点是否有替代方案。
- 3.2.2 经济可行性：开发/部署/运维成本，是否使用免费或低成本方案。
- 3.2.3 操作可行性：目标用户能否上手、管理端操作是否简化、培训成本。

每节 180–250 字，结论要明确“可行”，但理由要具体。

## 4. 第4章　系统设计（论文重心）

### 4.1　系统设计流程

#### 4.1.1　系统总体设计流程（约 250–300 字 + 图4.1）

写开发过程：需求分析→总体设计→数据库设计→功能开发→系统测试；每阶段产出什么。图4.1 后解释为什么按这个顺序。

#### 4.1.2　用户注册登录流程（约 250–300 字 + 图4.2）

写清：是否已有账号的判断、注册写入、登录校验、JWT 生成与保存、失败重试、登录后跳转。图4.2 的分支要逐条解释，不能只说“如图所示”。

#### 4.1.3　用户下单流程（约 250–350 字 + 图4.3）

写清：浏览→详情→选租期/地址/优惠券→提交→设备可租校验→地址/优惠券有效性校验→算价→扣库存建单→写快照/日志。重点写**校验顺序**与**失败回退**。

#### 4.1.4　订单支付与状态流转流程（约 250–350 字 + 图4.4）

- 状态机：待支付→待发货→使用中/待归还→已完成；取消/超时关闭。
- 支付：沙箱/模拟支付要如实说明；支付回调如何改状态；重复支付如何防。
- 取消/关闭：库存回滚、优惠券回滚、支付单关闭。
- 图4.4 后的注释句要与正文一致。

#### 4.1.5　系统操作流程（约 150–200 字）

从用户打开系统到完成一次核心业务的端到端路径；不要重复 4.1.2–4.1.4 的细节，只写跨模块协作。

### 4.2　系统总体结构设计

#### 4.2.1　系统架构设计（约 350–450 字 + 图4.5）

- 分层：客户端/接入层/业务层/数据层/外部能力；每层职责与边界。
- 鉴权：token 如何保存、拦截器如何解析、接口如何按角色限制、越权如何处理。
- 第三方/外部能力：接入方式 + 未启用时的降级路径（如 AI 工作流未配置不影响核心流程）。
- 图4.5 的每个连线标签都要在正文出现。

#### 4.2.2–4.2.4　各端功能结构（约 300–400 字 + 图4.6）

- 4.2.2 用户端：模块树 + 每个模块职责（对应第 5 章 5.1.x）。
- 4.2.3 管理端：模块树 + 管理动作（对应 5.2.x）。
- 4.2.4 后端业务模块：Controller/Service/Mapper 的职责划分，不写类清单。
- 图4.6 的模块名必须与第 5 章小节一致。

### 4.3　数据库设计

#### 4.3.1　概念结构设计（约 500–600 字 + 图4.7 + 每个实体一张属性图）

- 先用一段话概括核心实体与联系（谁和谁、什么关系、几对几）。
- 图4.7 总体 E-R 图；**图4.8 起为图4.7中的每一个实体各画一张实体属性图**，不是只画“用户”一张。
- 每个实体属性图前后用一句话引导/解释；属性数 3–8 个，只画业务重要字段。
- 图后解释：为什么这些实体是核心、哪些实体通过什么字段关联。
- 实体属性图数量必须与 E-R 图实体数一致；项目实体不同就改 `specs/entity-attributes.json` 后重新生成。

#### 4.3.2　逻辑结构设计（约 450–550 字）

按硬性大纲要求，必须包含：

1. **表间关系段**：订单表通过 user_id 关联用户、device_id 关联设备；支付记录通过 order_id 关联订单；评论通过 post_id 关联帖子；收藏通过 target_type+target_id 表达多态关系……（按实际表写）。
2. **实体字段清单**：每个核心实体一段，列出关键字段（不是全部字段），格式如：

> 用户（用户 ID、昵称、手机号、角色、状态、信用分、创建时间）；

3. 说明一对多/多对一/多态关系，以及快照字段（地址快照、设备快照）为什么存在。

#### 4.3.3　物理结构设计（约 350–450 字 + 每表一张三线表）

- 每张核心表：一句功能说明 + 三线表。
- 表列固定：`编号 | 字段名 | 类型 | 长度 | 是否非空 | 是否主键 | 注释`。
- **注释列 ≤4 个汉字**，只写语义（如“主键ID”“创建时间”“用户ID”），不写枚举/默认值/单位。
- 长表跨页：表头重复 + 续页标“续表X.Y”；表题注在表上方，表体不被拆开。
- 写关键索引与完整性约束（唯一索引防重、常用查询索引、外键/逻辑关联）。

**业务正确性设计（若涉及，必须写）**：并发扣库存、优惠券防重复使用、支付与订单状态一致性（事务/状态机/日志）、订单关闭时库存与优惠券回滚。

## 5. 第5章　系统实现

### 每节统一写法（约 250–320 字 + 1 张截图；12 节合计约 3000–3900 字）

1. **功能说明**：这个模块给谁用、解决什么问题（2–3 句）。
2. **交互路径**：用户从哪个入口进入、点哪些按钮、系统如何响应（按步骤写，但不要写成操作手册）。
3. **关键逻辑**：前端如何校验/传参，后端如何校验/落库/返回；涉及状态变化的写清前后状态。
4. **界面截图**：最终完成态，图注在下；图前有“如图5.x所示”，图后有 1–2 句说明图中关键区域。
5. **异常/边界**（可选）：无数据、未登录、参数非法时如何提示。

### 第5章禁止

- 放测试用例、测试结论（属于第6章）。
- 只放截图不写说明；或只写说明没有截图。
- 写“代码如下”并贴大段代码；关键逻辑用文字+短片段（≤10 行）即可。
- 写“由于篇幅有限，代码略”这种自我标注。

### 截图占位

模板用 `![图5.x　题注](PENDING:界面名)`；提交前替换为真实截图。截图要清晰、无测试脏数据、无水印错位、显示宽度 ≤15 cm。

## 6. 第6章　系统测试

### 6.1　测试目的（约 200–300 字）

说明验证什么：功能正确性、核心业务闭环、权限与异常、非功能约束。不要写“为了发现 bug”这种空话。

### 6.2　测试方法（约 250–350 字）

- 黑盒功能测试为主；辅以接口测试、边界值、异常场景。
- **测试环境表**：操作系统/语言版本/数据库版本/框架版本/浏览器或微信开发者工具版本/测试工具版本，必须填全，不得“后续补充”。

### 6.3　测试内容（约 600–800 字 + 用例表）

每类测试一张四列用例表：

| 编号 | 测试模块 | 测试操作 | 预期结果 |
|---|---|---|---|
| UT-01 | 用户登录 | 输入正确手机号与验证码 | 登录成功，返回 token，跳转个人中心 |
| UT-02 | 用户登录 | 输入错误验证码 | 提示“验证码错误”，不生成 token |
| BT-01 | 下单 | 库存为 0 时提交订单 | 提示库存不足，订单不创建，库存不变 |
| PT-01 | 权限 | 普通用户访问管理端接口 | 返回 403/无权限，不泄露数据 |

覆盖要求：

1. 各端功能（用户端、管理端）；
2. **核心业务闭环**：建单→扣库存→支付→状态流转→取消/回滚，每步断言；
3. **权限与异常**：未登录、越权、访问他人数据、参数非法；
4. 扩展功能（AI/推荐）降级可用性。

预期结果必须可验证（状态、数值、提示、数据库变化），不能写“功能正常”。

### 6.4　测试结论（约 250–350 字）

- 按模块/流程/权限逐条对应测试结果，不要出现“测试了 A 却结论说 B”。
- 如实写未覆盖/受限项（如沙箱支付、模拟物流）与原因。
- 不用“全部通过、系统完美”这类绝对化表述。

## 7. 结论、参考文献、致谢、附录

### 结论（600–900 字，2–4 段）

1. 完成了什么：系统范围、技术栈、核心闭环、测试结果（用数据/事实）。
2. 解决了什么问题：对应第 1 章提出的差距。
3. 局限：真实支付/物流未接入、数据规模有限、AI 依赖外部配置等。
4. 展望：可继续做的 2–3 个方向，具体可执行。

### 参考文献

- GB/T 7714 顺序编码制；正文 [n] 与文末一一对应。
- 只列真实读过的文献；官方文档可列（注明版本/URL/访问日期）。
- 不编造作者、期刊、卷期、页码、DOI；缺信息就换一篇能核实的。

### 致谢

半页到一页，真诚得体；不写班级昵称、网络流行语、大段私人叙事。

### 附录

只放真实内容（核心代码清单、完整数据字典、问卷）。没有内容就删掉本节，**不要留空标题**。

## 8. 语言与证据纪律

- 正文用“本文设计并实现了 / 本系统采用 / 该模块主要完成 / 测试结果表明”；禁止“根据源码 / 从代码看 / 待补充 / 占位 / 当前材料 / 本地路径 / 文件名”。
- 同一概念全文同名；中英文首次出现给对照。
- 不写“我觉得 / 大家都知道 / 特别牛 / 极致体验 / 遥遥领先”。
- 句子完整，避免 40 字以上长句；长短句交错。
- 每个图/表先引导后出现；图题注在下、表题注在上。
