# 设计规范

目标是"工程制图"气质：参考技术白皮书、咨询报告里的架构图——克制、干净、层级明确。不是海报，不是营销视觉。

## 配色

渲染器内置一套低饱和配色，通过 `tone` 选用，不要自己指定色值。

| tone | 填充 | 描边 | 文字 | 用途 |
|---|---|---|---|---|
| `default` | `#FFFFFF` | `#9AAAB8` | `#1F2933` | 一般模块（绝大多数） |
| `accent` | `#E8EFF6` | `#2F5D8A` | `#2F5D8A` | 本次要强调的模块 |
| `strong` | `#2F5D8A` | `#2F5D8A` | `#FFFFFF` | 唯一的核心/入口，一图最多一个 |
| `muted` | `#F4F6F8` | `#D7DEE5` | `#5B6B7A` | 弱化：容器、非重点层 |
| `ghost` | `#FFFFFF` | `#D7DEE5` | `#5B6B7A` | 外部系统、边界外对象 |
| `warn` | `#FBF1E4` | `#A86A22` | `#A86A22` | 风险、待改造、瓶颈 |
| `ok` | `#EAF3EE` | `#3F7A5E` | `#3F7A5E` | 已达标、已上线 |

中性色阶：文字 `#1F2933` → 次要 `#5B6B7A` → 注释 `#8A99A8` → 分隔线 `#D7DEE5`。连线 `#6E8091`。

**用量纪律**：一张图里 `tone` 不超过 3 种；`accent` 覆盖的模块数不超过总数的 1/4；`strong` 最多一个。颜色用来表达"重要性差异"，不是用来区分模块类别——分类靠分组和位置表达。

## 字号

| 元素 | 字号 | 说明 |
|---|---|---|
| 图标题 | 19pt 粗 | 左上，一句话说清是什么系统 |
| 副标题 | 9.5pt | 补充视角，如"分层架构 · 应用与数据两级解耦" |
| 分层标签 | 10.5pt 粗 | 层名，居中在左侧标签列 |
| 分组标题 | 9pt 粗 | 灰蓝色，左上角 |
| 模块名 | 11.5pt | 自动缩到放得下，下限 8pt |
| 模块副文字 | 8.5pt | 技术栈、协议、数量，下限 7pt |
| 连线标签 | 8pt | 协议名、动作名 |
| 图例 / 注释 / 页脚 | 8—8.5pt | 灰 |

字体固定：中文微软雅黑，西文 Arial。不要混入第三种字体。

## 线宽

容器 0.75pt，模块 0.9pt，连线 0.9pt，分隔细线 0.75pt。全图只用这四档。

## 间距

默认值（`layout` 可覆盖）：外边距 0.42in，层间距 0.17in，组间距 0.14in，层内边距 0.09in，同组模块间隙 0.10in。

比例关系比绝对数值重要：**层间距 ≈ 2 × 模块间隙，外边距 ≈ 2.5 × 层间距**。任何一处明显偏离，图就会显得"挤"或"散"。

## 图型配方

### 1. 分层架构（默认，80% 的场景）

从上到下：接入层 → 应用层 → 支撑层 → 数据层 → 基础设施层。左右可挂"标准规范体系""安全保障体系"两条竖栏（`rails`）。

```json
{ "bands": [
    { "id":"access", "label":"接入层", "height_in":1.05, "groups":[{"label":"服务对象","items":["Web 门户","移动端"]}] },
    { "id":"app",    "label":"应用层", "height_in":1.12, "groups":[{"label":"业务应用","items":["事项办理","综合查询","统计分析"]}] }
]}
```

适用：平台总体架构、系统技术架构、产品能力分层。评审最认这种。

### 2. 中心辐射

一个核心模块居中，周边模块环绕。用 `free` 绝对定位，核心用 `shape:"oval"`。

```json
{ "free": [
    { "id":"hub", "label":"数据中台", "x_in":5.3,"y_in":3.0,"w_in":2.7,"h_in":1.4, "shape":"oval","tone":"strong" },
    { "id":"a",   "label":"采集",     "x_in":1.6,"y_in":1.2,"w_in":1.9,"h_in":0.8 },
    { "id":"b",   "label":"治理",     "x_in":9.6,"y_in":1.2,"w_in":1.9,"h_in":0.8 }
  ],
  "flows":[ {"from":"a","to":"hub","label":"接入"}, {"from":"hub","to":"b"} ] }
```

适用：能力中枢、网关、单一入口型系统。

### 3. 部署拓扑

按网络区域分层（互联网区 / DMZ / 应用区 / 数据区），区域内放具体节点，用 `ghost` 表示外部或第三方。

适用：需要说清"什么东西部署在哪、跨不跨网"的场景。要点是区域边界比节点更重要，层名写清网络域。

### 4. 模块树

用 `bands` 表达层级：顶层一个模块，下面逐层展开，用 `groups` 控制每层分组。适合功能结构图、菜单结构、代码模块划分。

要点：同一父节点下的子节点必须相邻且等宽，否则读者会误判归属。

### 5. 数据流

左到右的流转用 `free` 摆成一条横向链路，箭头连接相邻节点。如果要"阶段 × 角色"的矩阵，用 `bands` 表示角色、`groups` 表示阶段。

要点：只画主干路径，分支最多一层。数据流图最容易画成蜘蛛网。

## 反例

- **彩虹配色**：每个模块一个颜色。读者会以为颜色有含义，实际没有。用 3 种 tone 封顶。
- **图标堆砌**：每个模块配一个小图标。在 12pt 的模块里图标只会抢文字的位置。
- **立体/阴影/渐变**：看起来像 2010 年的 PPT 模板。渲染器已强制关闭阴影，不要加回来。
- **箭头乱飞**：把代码里所有调用关系都画上。只画主干，分支靠文字说明。
- **层名写成技术名词**："Spring Boot 层""Kafka 层"不是分层，是技术选型。分层应该回答"这一层负责什么"。
- **没有图例**：用了 `accent`/`warn`/`ghost` 就必须给 `legend`，否则读者不知道蓝色代表什么。
- **文字塞满**：模块名超过 10 个字就该拆成 `label` + `sub`，或者换更短的词。
